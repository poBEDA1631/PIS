# Адендум №1 до Специфікації вимог (SRS)
## Проєкт: «Онлайн-каталог локальної бібліотеки»
### Тема: Списання фізичного примірника (Soft Delete / Decommissioning)

---

## 1. Контекст та обґрунтування зміни (Business Rationale)

У процесі експлуатації бібліотечного фонду фізичні примірники книг зношуються, знищуються внаслідок форс-мажорних обставин (наприклад, залиття водою, розрив сторінок) або остаточно втрачаються без можливості повернення читачем. 

Фізичне видалення запису про примірник із бази даних (`Hard Delete`) є неприпустимим, оскільки:
1. **Порушує цілісність інвентарного аудиту:** зникає історія про те, який інвентарний номер було присвоєно та яка була причина вибуття книги з фонду.
2. **Спотворює статистику використання:** втрачаються метрики попередніх видач та причин списання.
3. **Унеможливлює фінансову та матеріальну звітність** перед регуляторними органами.

Для розв'язання цієї проблеми впроваджується концепція **м'якого списання (Soft Delete)** шляхом введення термінального стану примірника **`DECOMMISSIONED` (Списано)**.

## 2. Нова функціональна вимога: REQ-F-ADD-001

### REQ-F-ADD-001: Списання фізичного примірника книги (`DECOMMISSIONED`)
* **Опис:** Система повинна надавати бібліотекарю можливість безповоротного виведення фізичного примірника книги з обігу шляхом встановлення термінального статусу `DECOMMISSIONED` зі збереженням запису в системі для аудиту та звітності.
* **Роль:** Бібліотекар (операція недоступна для читачів).
* **Життєвий цикл та правила переходу статусів (Domain Invariants):**
  1. Перехід у статус `DECOMMISSIONED` дозволено здійснювати **виключно** зі статусів:
     * `LOST` — примірник офіційно визнано втраченим або неповерненим після вичерпання термінів розшуку.
     * `IN_REPAIR` — примірник визнано непридатним до відновлення під час реставраційних робіт.
  2. Спроба переведення примірника у статус `DECOMMISSIONED` зі статусів `AVAILABLE`, `BORROWED` або `RESERVED` **категорично заборонена** і повинна відхилятися системою з кодом `HTTP 422 Unprocessable Entity` (Problem Details: `invalid-status-transition`), оскільки списанню книги обов'язково має передувати фіксація факту її втрати або неможливості ремонту.
  3. Статус `DECOMMISSIONED` є **термінальним**: будь-які переходи з нього у будь-які інші статуси (наприклад, у `AVAILABLE` чи `RESERVED`) заборонені.

## 3. Вплив на суміжні функціональні вимоги

### 3.1. Вплив на REQ-F-002 (Розрахунок `TitleAvailability` та `CopiesSummary`)
* Примірники у статусі `DECOMMISSIONED` не вважаються доступними для читача (`available = 0`).
* Якщо всі фізичні примірники книги перебувають у статусах `LOST` або `DECOMMISSIONED` (або фонд вичерпано), агрегований стан доступності книги `TitleAvailability` визначається як `OUT_OF_STOCK` ("Відсутня у фонді").
* Модель `CopiesSummary` розширюється числовим полем `decommissioned` для обліку кількості списаних одиниць у картці книги.

### 3.2. Вплив на REQ-F-004 (Архівування книги `isArchived`)
* Переведення бібліографічної картки книги в стан `isArchived = true` дозволяється, якщо всі пов'язані з нею примірники мають статус `LOST` **або** `DECOMMISSIONED`. Наявність примірників у статусах `AVAILABLE`, `BORROWED`, `RESERVED` чи `IN_REPAIR` блокує архівацію з кодом `HTTP 422`.

---

## 4. Критерії прийняття (Acceptance Criteria)

1. Перелік статусів `CopyStatus` розширено значенням `DECOMMISSIONED`.
2. Операція `PATCH /api/v1/copies/{inventoryNumber}/status` із цільовим статусом `DECOMMISSIONED` повертає `HTTP 200 OK`, якщо поточний статус примірника `IN_REPAIR` або `LOST`.
3. Операція `PATCH /api/v1/copies/{inventoryNumber}/status` із цільовим статусом `DECOMMISSIONED` повертає `HTTP 422 Unprocessable Entity`, якщо поточний статус примірника `AVAILABLE`, `BORROWED` або `RESERVED`.
4. Зміна статусу на `DECOMMISSIONED` доступна виключно користувачам з роллю «Бібліотекар» (при спробі читача повертається `HTTP 403 Forbidden`, без автентифікації — `HTTP 401 Unauthorized`).
5. У відповіді `GET /api/v1/books/{id}` об'єкт `copiesSummary` містить поле `decommissioned`.
6. Будь-яка дія зі списання фіксується в аудит-лозі Winston із фіксацією інвентарного номера, попереднього статусу, автора дії та коментаря (причини списання).

## 5. BDD-сценарії (Behavior-Driven Development)

### Сценарій 4.1: Успішне списання пошкодженого примірника з ремонту
```gherkin
Feature: Списання фізичного примірника книги
  As a Бібліотекар
  I want Переводити безнадійно пошкоджений примірник у статус DECOMMISSIONED
  So that Фондовий облік був точним, а примірник зберігався в системі для аудиту

  Scenario: Успішне списання примірника зі статусу IN_REPAIR
    Given Фізичний примірник книги з інвентарним номером "INV-1004" має статус "IN_REPAIR"
    When Бібліотекар змінює статус примірника "INV-1004" на "DECOMMISSIONED" з коментарем "Залито водою, відновленню не підлягає"
    Then Статус примірника "INV-1004" стає "DECOMMISSIONED"
    And Примірник враховується як списаний у copiesSummary картки книги
```

### Сценарій 4.2: Спроба списання доступного примірника безпосередньо з полиці
```gherkin
  Scenario: Відхилення списання примірника у статусі AVAILABLE
    Given Фізичний примірник книги з інвентарним номером "INV-1001" має статус "AVAILABLE"
    When Бібліотекар намагається змінити статус примірника "INV-1001" на "DECOMMISSIONED"
    Then Система відхиляє запит з HTTP-кодом 422
    And Тіло відповіді містить Problem Details із зазначенням неприпустимого переходу статусу
    And Статус примірника "INV-1001" залишається "AVAILABLE"
```
